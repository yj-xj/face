课题背景

从算法调用走向系统化实现

人脸替换并不仅仅是单次算法推理。若要将其用于课程设计或毕业设计展示，还需要解决素材导入、参数配置、任务执行、结果预览、文件管理与交互反馈等工程问题。

研究意义

验证桌面系统闭环能力

本课题的意义在于把人脸替换能力封装为一个可运行的桌面系统，通过前后端协同、数据库记录和视频处理流程，体现软件工程方向毕业设计的综合实现工作量。

系统目标

可演示、可管理、可归档

系统目标包括提供双模式操作入口，支持素材的统一管理与查询，完成处理结果的保存与回放，并在论文中以真实截图与真实样本数据验证实现效果。

System Features

系统功能

这一部分对应论文中的需求分析与详细实现章节，重点展示系统实际具备的功能模块，而不是展示型宣传文案。

视频模式处理

支持导入输入视频与目标人脸素材，完成读取、帧处理、输出写入与结果保存，适合展示完整的离线处理链路。

摄像头模式演示

提供摄像头实时模式，用于课堂展示或答辩演示，重点体现前端交互、线程控制与实时显示的协同实现。

素材管理

对人脸图片、输入视频等素材进行统一管理，避免演示时依赖手工查找文件，提高系统可用性与操作清晰度。

结果回放

处理完成后可直接查看输出结果，便于在答辩时展示输入与输出之间的差异，并支撑测试部分的案例分析。

数据库归档

将素材和输出结果写入数据库，保留文件路径、时长等信息，形成可检索的记录，为系统化设计提供数据支撑。

状态提示与异常处理

通过界面提示、任务状态反馈和基础异常保护，降低演示过程中的中断风险，也为后续日志治理预留改进空间。

双模式工作流

视频模式与摄像头模式并行构成完整功能闭环

视频模式

  • 选择输入视频与目标人脸素材
  • 加载检测与替换参数
  • 执行视频帧处理与结果写出
  • 保存输出记录并支持回放

摄像头模式

  • 连接摄像头设备并初始化线程
  • 实时采集图像帧并进行处理
  • 在界面中持续展示处理结果
  • 用于课堂演示和交互式验证
核心使用流程

典型用户操作路径

  1. 导入或选择人脸图片与输入视频。
  2. 在界面中完成模式切换与参数确认。
  3. 启动处理任务并观察状态反馈。
  4. 查看输出视频、回放处理结果。
  5. 将结果归档到数据库并用于论文案例展示。
Architecture

技术路线与系统架构

技术路线以“前端交互层 + 业务控制层 + 媒体处理层 + 数据持久化层”为主线，体现系统设计思路与模块间的数据流转关系。

Layer 01 前端交互层 由 PyQt5 负责窗口组织、模式切换、素材选择、状态反馈与结果展示，直接服务于答辩演示的可操作性。
Layer 02 业务控制层 负责调度模式切换、任务启动、参数传递和结果回写，是前端界面与底层处理逻辑之间的桥接层。
Layer 03 媒体处理层 结合 OpenCV、InsightFace 与传统图像处理流程，对图像或视频帧完成检测、对齐、替换、融合与写出。
Layer 04 数据持久化层 通过 Django REST 与 SQLite 管理素材信息、输出结果和路径记录，为查询、回放与论文统计提供依据。
技术栈

核心组件与处理管线

Python PyQt5 OpenCV Django REST SQLite InsightFace Dlib QThread

模块协作说明

  • 前端界面组织用户输入，触发视频模式或摄像头模式的具体任务。
  • 业务控制模块将素材路径和参数传入人脸处理流程。
  • 媒体处理模块负责逐帧运算、结果融合和视频写出。
  • 数据库与文件目录共同承担归档与结果查询职责。
01
输入素材 读取人脸图片、输入视频或摄像头画面，完成资源合法性检查。
02
检测与对齐 对图像中的人脸位置和关键点进行定位，为后续替换提供基础。
03
替换与融合 将目标人脸特征映射到输入画面，并进行边缘融合与结果修正。
04
结果写出 在视频模式中持续写出输出帧，在实时模式中同步回显结果画面。
05
归档与回放 将输出文件与关键信息写入数据库，供系统查询、回放与测试分析使用。

核验结果

当前可确认的问题与改进方向

路径一致性抽查

  • 人脸素材路径存在校验：9 / 9。
  • 输入视频路径存在校验：7 / 8。
  • 输出文件总数高于数据库记录数，说明仍需继续完善归档一致性与清理策略。

已知问题

  • 路径治理仍需加强，数据库记录与实际文件之间还存在个别不一致样本。
  • 批量任务调度能力较弱，当前更适合课程展示和单任务验证。
  • 异常日志展示仍然偏简化，后续需要细化错误信息与恢复策略。
  • 不同设备环境下的实时模式稳定性仍有优化空间。
